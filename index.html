CogniCode makes opencode a tutor instead of a typist. The model asks how you would approach the problem, explains the parts you haven't met, and cannot write a single line until you approve an exact scope and file list. The approval is recorded by the plugin — not promised by the model.

Fig. 02 — three parts, no build step

A skill, a guard, and a state file.

Everything ships as one plugin file and two skills inside .opencode/. opencode discovers it at startup. There is no marketplace, no hook JSON, and nothing to compile.

Plate A

The skill

/cognicode-learn loads a behavior guide for the whole conversation: ask for your approach, teach, never quietly substitute your judgment. It carries no power of its own — only the plugin's tools change anything.

A skill the model cannot reach: permission.skill keeps an ordinary build request from turning into a lesson.

Plate B

The guard

A tool.execute.before hook refuses the write. While a decision is open, write, edit, patch and mutating shell commands are rejected by opencode itself, with an error that names the decision and the next step.

After approval, writes are compared against the approved file list.

Plate C

The state

.cognicode/state.json holds engagement, mode, preferences, the open decision and the approved scope. Seven tools are the only thing that may change it — including your approval.

profile.md progress.md project-map.md decisions.md

Fig. 03 — enforcement, not a request

What the guard allows,
and what it refuses.

A blocked call is never a dead end: it is an error the model reads and answers by asking you. That is the whole loop.

While a decision is open

  • read · glob · grep · list
  • question · task · skill · todowrite
  • writes inside .cognicode/ (your notes)
  • ls · cat · rg · sed -n
  • git status / log / diff / show
  • node --version

While a decision is open

  • write · edit · patch · notebookedit
  • npm test · bun run build
  • rm · mkdir · curl
  • redirects · sed -i · find -delete
  • git commit / push / checkout
  • gh pr create · node -e
  • env · command wrappers · awk

After you approve

  • the listed files and directories
  • any shell command, including builds
  • tests, formatters, verification
  • writes inside .cognicode/

After you approve

  • any file outside the scope
  • reported back as scope creep
  • the previous approval is dropped
  • when the next checkpoint opens

▸ what the model sees when it tries anyway

CogniCode guard: unresolved implementation checkpoint "Search". Ask the learner, record the outcome with cognicode_resolve, then retry. File writes and mutating shell commands stay blocked; do not work around the guard.

The shell check is a deny-list heuristic, not a sandbox. opencode's own permission rules still apply on top, and cognicode_state reports any tool the guard cannot classify rather than letting it pass unnoticed.

Fig. 04 — three checkpoints, not three mandatory stops

Where you enter the loop.

Several Build checkpoints can lead to one confirmation, and an Implementation checkpoint also confirms the design — so a separate Design checkpoint is often unnecessary. On either confirmation, Discuss suspends the decision and invites questions. Nothing is recorded, and writes stay blocked.

01 / reasoning

Build checkpoint

How would you approach this problem? Reasoning happens in chat, in plain English, and the model waits.

“A links table with note_id and folder_id.”

02 / confirmation

Design checkpoint

Is this the right design? Confirm and continue records it and keeps planning — it does not authorize code.

Two options: a join table, or a JSON array on the folder.

03 / approval

Implementation checkpoint

Is this the right code, in this scope? Implement this step authorizes exactly the scope and file list shown.

Scope + every file, before a single byte is written.

Fig. 06 — install

Three ways in.

Requires opencode 1.18 or newer. Nothing else — no Python, no marketplace, no build step. Restart opencode afterwards; plugins and skills are read once at startup.

One project

Copy the plugin and both skills into the project you want to work in.

$ scripts/install.sh ./my-project

Every project

Install into ~/.config/opencode once and it is available everywhere.

$ scripts/install.sh --global

Then start

Run this in the project. Setup asks one question at a time; choose Use defaults to skip it.

/ cognicode-learn

Notes are yours

.cognicode/ holds profile, progress, project map and the decision ledger. Add it to .gitignore — CogniCode suggests it, never edits it silently.

Say it in chat

“Use fewer checkpoints.” “Focus on backend.” “Just implement this one.” “Pause learning.” No commands, no config editing.

Start over

/cognicode-reset previews, backs up to .cognicode/backups/, and re-runs onboarding. Code is never touched.

Verify

opencode debug skill lists both skills. opencode debug agent build lists the seven tools.
